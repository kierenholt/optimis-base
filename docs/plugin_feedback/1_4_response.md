## 2. Rejected Proposals (Not Worth It / Could Lead to Other Issues)

These 3 suggestions from the feedback reports either **weaken core transactional invariants** or **introduce brittle false-positives**:

### 2A. Auto-Committing `ctx.plugin_db.exec()` or Allowing Mid-RPC `commit()` Before `ctx.http` *(Parent DMZ §2D)* — **REJECT**
* **What was suggested:** Auto-commit every `ctx.plugin_db.exec()` call (or allow committing `WriteDB` mid-function) so a plugin can write a `'PENDING'` row to `plugin_db`, make an outbound `ctx.http.post` call, and then write `'COMPLETED'` in the same RPC call.
* **Why it is rejected:**
  1. **Destroys Single-Transaction RPC Atomicity:** Currently, [`ExecuteRPC`](file:///home/kieren/Documents/code/optimis/internal/host/host.go#L550-L624) guarantees that if an endpoint executes multiple `ctx.plugin_db.exec()` statements and then hits a Lua runtime error, the entire `WriteDB` transaction rolls back cleanly. Auto-committing each `.exec()` leaves partial, corrupted writes in `plugin_<name>.db` on mid-endpoint failures.
  2. **Breaks Post-Commit Event Bus Consistency:** `ctx.events.emit()` buffers events until the single `writeTx` commits at the end of the RPC call. Splitting a single RPC into multiple transactions means events could be emitted for half-finished workflows.
  3. **The 3-Stage Pipeline Already Solves This:** Reading from `ReadDB` $\rightarrow$ executing outbound `ctx.http` $\rightarrow$ writing the final result (`SYNCED` or `FAILED`) in a single atomic `WriteDB` transaction at the end is already proven in both `lms_sync_plugin` and `parent_dmz_plugin`.

### 2B. Regex-Scanning Outbound `ctx.http` Bodies for 13-Char `UPN` / 10-Digit `ULN` (`disallow_statutory_identifiers`) *(Parent DMZ §2C)* — **REJECT**
* **What was suggested:** Have the Go Host regex-scan outbound `ctx.http` request payloads and block requests containing a 13-char `UPN` or 10-digit `ULN`.
* **Why it is rejected:**
  1. **High False-Positive Rate:** A 10-digit `ULN` pattern (`\b\d{10}\b`) matches every Unix epoch timestamp (e.g. `1730156400`), 10-digit phone number, or numeric ID in JSON payloads, which would randomly break legitimate outbound syncs in production.
  2. **Wrong Layer for PII Filtering:** Preventing statutory IDs from leaking to non-statutory plugins belongs at the **Core DAL projection layer**, not via brittle regex inspection of serialized HTTP strings.

### 2C. Adding `data-mis-form="#form-id"` / `data-mis-args-fn` Magic DOM Scraping to `mis-bridge.js` *(Timetable §2C, LMS Sync §2C)* — **NOT WORTH IT**
* **What was suggested:** Add automatic `<form>` DOM scraping or global callback attributes to [`sdk/ui/mis-bridge.js`](file:///home/kieren/Documents/code/optimis/sdk/ui/mis-bridge.js) so dynamic forms don't need to update `data-mis-args`.
* **Why it is rejected:**
  * Real school UIs (like a 30-row attendance register or multi-column markbook) submit nested arrays of typed objects (`marks: [{ pupil_id, attendance_code, minutes_late }]`), which flat HTML `<form>` scraping cannot serialize cleanly without brittle type-coercion rules.
  * [`sdk/ui/mis-bridge.js`](file:///home/kieren/Documents/code/optimis/sdk/ui/mis-bridge.js) *already* provides `window.mis.rpc(method, args)` for dynamic JS forms while `data-mis-rpc` handles declarative buttons. We simply ensure `mis-sdk verify` (Section 8B) accepts both `data-mis-rpc` and `window.mis.rpc()`.
